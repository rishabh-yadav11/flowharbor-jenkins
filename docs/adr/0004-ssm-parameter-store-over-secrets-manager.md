# ADR 0004 — SSM Parameter Store instead of Secrets Manager

- **Status:** Accepted
- **Context:** The pipeline writes per-release values (`GIT_AUTHOR`, `PIPELINE_URL`) that the task definition must receive as secrets at launch, and the same values have to be readable and overwritable by a Jenkins job without a Terraform state change.
- **Decision:** The two values live as `SecureString` parameters under `/flowharbor/<env>/…` created by Terraform with `lifecycle { ignore_changes = [value] }` so an apply never reverts a Jenkins-written value (`terraform/modules/ecs/main.tf:92`, `terraform/modules/ecs/main.tf:107`), and reach the container through the ECS `secrets` block rather than plaintext `environment` (`terraform/modules/ecs/main.tf:147`, `terraform/modules/ecs/main.tf:168`) — an invariant the pipeline re-checks against the registered task definition after every deploy (`Jenkinsfile:747`, `Jenkinsfile:748`).
- **Consequences:** A secret value rotates by `aws ssm put-parameter --overwrite` inside the pipeline, Terraform never has to know the value, and the deploy assertion can prove the value is not sitting in the task definition's plaintext environment; the cost is that SSM has no native rotation policy, and a SecureString value is still readable by anything holding the IAM permission that reads it.
- **Rejected alternative:** AWS Secrets Manager — rejected because it adds a per-secret monthly charge and a rotation lifecycle to two values that are re-written on every single release, while Parameter Store is already required for the agent/controller handshake values the bootstrap script writes over (`terraform/user-data/jenkins-master.sh:259`).
