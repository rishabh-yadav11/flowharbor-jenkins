# ADR 0001 — Releases are tag-driven and manually triggered

- **Status:** Accepted
- **Context:** A demo/portfolio stack needs a delivery path that is auditable, reproducible, and demonstrable by a reviewer with no cloud account; webhook-driven or multibranch pipelines add an external dependency (a reachable GitHub App, SCM credentials in Jenkins, or a polling loop) that cannot be exercised offline, and "auto-deploy on merge to main" makes every merge a production event.
- **Decision:** Every release is triggered by a human starting one of three jobs (`flowharbor-dev`, `flowharbor-staging`, `flowharbor-prod`) with a `GIT_TAG` parameter; the jobs are manual-only with no SCM polling and no GitHub trigger (`terraform/user-data/flowharbor-jobs.groovy:9`, `terraform/user-data/flowharbor-jobs.groovy:31-35`). The tag is resolved to a commit SHA and that SHA — not a branch — is checked out (`Jenkinsfile:200`, `Jenkinsfile:207`).
- **Consequences:** A release is a deliberate act with a named human in the audit log, and the same tag promotes through all three environments, so dev/staging/prod cannot drift onto different commits; the cost is that nothing ships on its own, and a forgotten tag blocks the pipeline with `GIT_TAG parameter is required…` (`Jenkinsfile:189`).
- **Rejected alternative:** A GitHub push webhook into Jenkins (or a multibranch pipeline) — rejected because it makes "which commit is live" a function of a remote service's timing, and it cannot be demonstrated without a live controller, a public endpoint, and SCM credentials in the trust model.
