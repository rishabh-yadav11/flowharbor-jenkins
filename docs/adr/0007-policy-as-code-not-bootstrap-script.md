# ADR 0007 — Policy as code (JCasC + Job DSL), not inline Groovy in the bootstrap script

- **Status:** Accepted
- **Context:** The controller's authorization strategy, security realm, and its three delivery jobs used to be created by inline Groovy posted to `/scriptText` from `jenkins-master.sh`, with the RBAC model existing only as a comment. That made the security posture unreviewable, made the GitHub remote a hardcoded string, and lost the whole configuration on every controller rebuild.
- **Decision:** The controller's policy is a versioned file in the repository — `jenkins/casc/jenkins.yaml` sets the mode, `numExecutors: 0`, the local realm, the matrix authorization entries, and `remotingSecurity` (`jenkins/casc/jenkins.yaml:39`, `jenkins/casc/jenkins.yaml:43`, `jenkins/casc/jenkins.yaml:51`, `jenkins/casc/jenkins.yaml:73`) — and the jobs come from a Terraform-rendered Job DSL file that the bootstrap script writes to disk *before* the service starts (`terraform/user-data/jenkins-master.sh:161`), so the controller's unit only has to point at a URL (`terraform/user-data/jenkins-master.sh:227`). Authorization is `matrix-auth`'s `globalMatrix`, not role-strategy: role-strategy 3.x exposes no JCasC symbol for `authorizationStrategy`, so the `roleBased` form never configured.
- **Consequences:** A reviewer reads the entire RBAC model in git, the GitHub remote is the Terraform variable `github_repo` instead of a literal, and a controller rebuild reproduces the same jobs; the cost is a hard ordering constraint — `jenkins/casc/jenkins.yaml` must exist on the default branch before the first `terraform apply`, because a fetch failure or a malformed file aborts the controller boot instead of degrading.
- **Rejected alternative:** Inline Groovy in the bootstrap script — rejected because it cannot express the authorization strategy, cannot be reviewed as policy, and hardcodes the SCM remote. The `jobs: - file:` form was also chosen over a *seed job* triggered after boot, and that was forced rather than preferred: with `numExecutors: 0` the controller cannot run a seed job at all, so the DSL is already on disk when the import happens, and the bootstrap asserts the three jobs exist afterwards instead (`terraform/user-data/jenkins-master.sh:347`).
